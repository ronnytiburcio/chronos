# Chronos — project notes for Claude Code

Native macOS desktop time tracker: a clickable panel at desktop-icon window level (behind app windows), one-click project timers, automatic daily rollover that archives to CSV/markdown. Open source, MIT. Full spec: `docs/SPEC.md`. Build plan with locked decisions: `~/.claude/plans/take-a-look-at-linked-wirth.md`.

## Stack
- Swift 6 language mode, strict concurrency. SwiftUI views hosted in AppKit windows. No third-party dependencies.
- Deployment target macOS 14. Local machine runs macOS 27 beta / Xcode 27 beta; CI runs `macos-26` (Xcode 26.6). Keep APIs <= macOS 14 and avoid Xcode-27-only project features.
- App entry is pure AppKit (`Chronos/App/ChronosApp.swift` -> `AppDelegate`), not a SwiftUI `App` scene, because the app is an `LSUIElement` agent with an `NSPanel` at desktop level.

## Project definition
- `project.yml` (xcodegen) is the source of truth. `Chronos.xcodeproj` is generated and committed so cloners just open it.
- After adding/removing source files or editing `project.yml`: `xcodegen generate` then commit the regenerated xcodeproj.
- `Info.plist` is generated into `Chronos/Resources/Info.plist` by xcodegen from the `info:` block; edit `project.yml`, not the plist.

## Commands
```bash
xcodegen generate
xcodebuild -project Chronos.xcodeproj -scheme Chronos -destination 'platform=macOS' build
xcodebuild -project Chronos.xcodeproj -scheme Chronos -destination 'platform=macOS' test
open Chronos.xcodeproj
```
Run the built app: `open "$(xcodebuild -project Chronos.xcodeproj -scheme Chronos -showBuildSettings | awk '/ BUILT_PRODUCTS_DIR/{print $3}')/Chronos.app"` (or Cmd-R in Xcode). Quit via the menu bar bolt -> Quit.

## Release & CI
- One workflow, `.github/workflows/build.yml` (name: **Build**), both jobs on `runs-on: macos-26`, Xcode pinned to `/Applications/Xcode_26.6.app` when it exists and the runner default otherwise.
  - **`test`** — every push (branches and tags) and every pull request: `xcodebuild ... test`, then a grep for absolute home and volume paths over the repo, with one character of each needle bracketed so the workflow does not match its own pattern. Personal *names* are deliberately not in the public pattern (that would put them in the repo); check for them locally before pushing: `grep -rniE "<name>|<drive>" --exclude-dir=.git .`.
  - **`release`** — tag push `v*`, `needs: test`, `permissions: contents: write`: universal Release build (`ARCHS="arm64 x86_64" ONLY_ACTIVE_ARCH=NO CODE_SIGN_IDENTITY=- CODE_SIGN_STYLE=Manual DEVELOPMENT_TEAM=` into `-derivedDataPath build`), `lipo -info` gate that fails unless both arches are present, `codesign --force --deep --sign -`, `Scripts/make-dmg.sh` -> `dist/Chronos-<tag>.dmg`, `gh release create` with the CHANGELOG section for that version as the notes (`--prerelease` when the tag has a suffix such as `v0.1.0-rc1`).
- **Cutting a release:** move the `## [Unreleased]` entries into a new `## [X.Y.Z] - YYYY-MM-DD` section in `CHANGELOG.md`, bump `MARKETING_VERSION` in `project.yml` and `xcodegen generate`, commit, then `git tag vX.Y.Z && git push origin vX.Y.Z`. The tag push is what builds and publishes; nothing else does.
- **Optional Developer ID signing + notarization** is skipped unless the secrets exist. `if:` cannot read `secrets`, so a prior step writes `HAS_SIGNING` into `$GITHUB_ENV` and the notarize step keys off that. Secrets: `DEVELOPER_ID_CERTIFICATE_P12` (base64 of the .p12), `DEVELOPER_ID_CERTIFICATE_PASSWORD`, `DEVELOPER_ID_IDENTITY`, `APPLE_ID`, `APPLE_TEAM_ID`, `APPLE_APP_PASSWORD`. Without them the release ships ad-hoc signed and the release notes carry the `xattr -d com.apple.quarantine` instructions.
- `Scripts/make-dmg.sh <app> <out.dmg>` stages a temp folder (app + `Applications` symlink) and runs `hdiutil create -format UDZO`. No `create-dmg` dependency. Verified locally: universal 3.7M app, 1.5M `.dmg` that mounts with `Chronos.app` and `Applications`. `spctl --assess` says **rejected** on the ad-hoc build, which is expected and is exactly what the README's Gatekeeper section documents.
- On macOS 27 beta `hdiutil create/attach/detach` print a deprecation warning and still work; `macos-26` does not.

## Conventions
- Everything UI/model is `@MainActor`; model objects are `@Observable`.
- Totals are always computed from session timestamps, never from counters.
- "Today" = sessions with `start >= state.lastRollover`. Tracking day runs rollover-to-rollover (default 04:00).
- Storage: `sessions.jsonl` append-only (open/close/adjust/delete records; an edit or a deletion is a new line, never a rewrite), `projects.json` + `state.json` written atomically (temp + rename).
- Session-edit timestamp rules (start before day, start in future, reopening a closed session, end before start, end in future) live in one place, `SessionEditing.validationError`; `TimerEngine.editSession` and `SessionEditRow`'s Save button both call it, so the row can never grey out Save for a reason the engine would accept, or vice versa.
- Archive CSV rows only for projects with > 0 seconds; empty days write nothing but still advance `lastRollover`.
- No network code, ever. No personal names/paths in the repo; all paths from `FileManager`.
- Build in vertical slices; each phase ends runnable. Verify gate = `/phase-review` (+ `/code-review` for phases 2, 3, 5).

## Gotchas
- `DesktopPanel` must be created with `.nonactivatingPanel` in the style mask at init and never mutated afterwards, or keyboard input silently breaks.
- Window level is `CGWindowLevelForKey(.desktopIconWindow) + 1` so Finder's desktop-icon layer cannot swallow clicks. Verified live: the panel reports `kCGWindowLayer == -2147483602`.
- `NSHostingView` subclass overrides `acceptsFirstMouse` so the first click acts without activating the app.
- The panel's content view is the `NSVisualEffectView`; the hosting view is its subview. Rounded corners live on the effect view's layer (`cornerRadius` + `masksToBounds`), which is also what gives the window a rounded shadow.
- `.hudWindow` follows the *system* appearance, so the panel pins `appearance = NSAppearance(named: .darkAqua)` and adds an Ink `#15171C` tint view between the material and the hosting view. Without both, the panel reads as light grey glass on a light wallpaper and SPEC §9's Paper text is unreadable.
- `WindowPlacement.resolvedFrame` honours the saved *origin* but always applies the caller's size, so a frame saved by an older build cannot resurrect a stale panel height.
- `AppState.windowFrame` is encoded with named keys (`x`, `y`, `width`, `height`) via a custom `Codable`; `CGRect`'s synthesized Codable would write nested arrays.
- `ChronosTests` uses the app as its test host. `AppDelegate` skips all setup when `XCTestConfigurationFilePath` is in the environment, so tests never show the panel or touch the real state file. Tests that touch storage still take an injected file URL and use a temp directory.
- **`TimerEngine` is the single owner of `AppState`** (window frame, `lastRollover`, `settings`) and the only writer of `state.json`. `AppDelegate` builds it at launch and hands its `windowFrame` to `PanelController`, whose frame-change closure calls `engine.updateWindowFrame(_:)`. One owner means a frame save can never clobber the rollover bookkeeping sitting in the same file — do not add a second writer.
- `TimerEngine` takes `Clock`, `ProjectStore`, `SessionLog`, `AppStateStore`, a `Calendar`, and an `ArchiveLocation` in its init so tests run against temp dirs and a fake clock. Every mutation is write-through: it persists before the method returns.
- The 1s ticker only runs while a session is open, and `tick()` re-reads `clock.now()` rather than accumulating, so sleep/wake stays correct. It is a target/selector `Timer` on `RunLoop.main` in `.common` mode whose target (`TickTarget`) holds the engine weakly; do not switch it to a block-based timer, which would capture the engine strongly (and `Timer` is not `Sendable` under Swift 6).
- `SessionLog` replay is forgiving: a corrupt line, a leading BOM, a `close` with no `open`, or a duplicate `open` is logged via `NSLog` and skipped, never thrown; an `open` while another session is still open closes the earlier one at the new start. An unrecognized `"type"` (an old build's file read by a newer one, or a newer file read by an old build) is skipped the same way. `rotate(to:)` refuses to overwrite an existing archive.
- `adjust`/`delete` replay, same forgiving spirit: for a given session id the **last** record wins. `adjust` for an unknown or already-deleted id logs and is skipped; it sets `start`, sets `projectID` only when present, and sets `end` only when present — an omitted `end` on an already-closed session is a no-op, never a reopen, so a reordered or hand-edited log can never resurrect a second ticking timer. `delete` is terminal: the row drops out of the result (never rewritten), `openIndex` is cleared if it pointed at the deleted row so a later stray `open` never force-closes a ghost, and any `close`/`adjust` recorded for that id afterward is ignored.
- Dates in every JSON file go through `JSONDates` (ISO-8601 with fractional seconds; whole-second input still parses).
- `TimerEngine.start` clamps the session start to `lastRollover` so a backward clock jump cannot start a session outside today.
- Tests for `@MainActor` types override `setUp() async throws` / `tearDown() async throws`, not the `WithError` variants — only the async hooks inherit the class's actor isolation, otherwise every shared property is a concurrency warning.
- `WindowPlacement` validates a saved frame against full screen frames (the user may park the panel under the Dock) and uses the main screen's `visibleFrame` only for first-launch placement.
- All JSON goes through `JSONFile` (atomic `Data.write`, ISO-8601 dates, sorted keys). Colors come from `Palette` in `Chronos/UI/Palette.swift`.
- **Panel height is `PanelLayout.height(rowCount:)`, pure arithmetic, not measured layout.** `PanelController` sizes the window from it at launch, and `PanelView` reports a new height through `onDesiredHeightChange` when `engine.visibleProjects.count` changes. The view's constants (`headerHeight`, `footerHeight`, `rowHeight`) are applied with `.frame(height:)` on the matching views, so the arithmetic and the drawing cannot drift — change one and change the other. Resizing keeps the panel's **top** edge fixed (Cocoa origin is bottom-left, so `origin.y` moves by the delta) and never animates. Note the asymmetry across launches: `WindowPlacement` restores the saved *origin* and applies the new size, so a relaunch with a different project count keeps the bottom-left corner, not the top.
- **Buttons in the panel must be `.buttonStyle(.plain)` over a `.contentShape(Rectangle())`.** Bordered/prominent styles want focus before they act, which costs a click in a panel that never activates. Plain buttons fire on the first mouse-down (with `FirstMouseHostingView`'s `acceptsFirstMouse`).
- **Inline text fields need `await PanelKeyWindow.makeKey()` before setting focus.** The panel is `becomesKeyOnlyIfNeeded = true`, so a field that *appears* after a button press never gets key status on its own. `panel.makeKey()` works (verified live: the panel reports `isKeyWindow == true` while Chrome stays frontmost, and typed characters land in the field) — but the `@FocusState` must be set on the *next* run-loop turn, because `makeKey()` leaves the panel itself as first responder and a same-pass focus is thrown away.
- **Row menus are AppKit `NSMenu`s (`RowMenu.swift`), opened from the row's `•••` button and from right-click via `menu(for:)`.** SwiftUI's `.contextMenu` never appears in the live panel because Chronos is never the active app; an `NSMenu` popped from an `NSView` works regardless (the same way status-bar menus do).
- **Escape needs a local `NSEvent` monitor (`View.onEscape(while:perform:)`).** Neither `onExitCommand` nor `onKeyPress(.escape)` fires while a SwiftUI `TextField` is editing on macOS 14+; both were tried in the live panel and neither reached the view. The monitor stores its action on a `@MainActor` class so nothing non-`Sendable` is captured by the `@Sendable` monitor closure, and only `Void` crosses out of `MainActor.assumeIsolated` (`NSEvent` is not `Sendable`).
- `MenuBarController` refreshes off `withObservationTracking` on the engine (`now`, `openSession`, `projects`, `settings`, `sessions`), re-arming inside the `onChange` hop; there is no second timer. `onChange` fires before the value is applied and off the main actor, hence the `Task { @MainActor ... }`. Re-arming also refreshes, so refresh exactly once per change.
- Ad-hoc code signing (`CODE_SIGN_IDENTITY=-`) is required even for local runs: `SMAppService` login-item registration fails on unsigned binaries.
- Writing to `~/Documents` triggers a one-time TCC prompt; `NSDocumentsFolderUsageDescription` is set in `project.yml`.
- **Rollover lives on `TimerEngine`, not a separate engine.** `performRolloversIfNeeded(now:)` loops `while TrackingDay.next(after: lastRollover) <= now`, running `performRollover(at: boundary)` once per missed day in order; `resetDay()` first runs the catch-up, then the same routine with `clock.now()` as the boundary. `nextRolloverBoundary` is the one place the "when" is computed; `RolloverScheduler` arms its timer from it and shares the engine's `clock`. **Anything that changes `settings.rollover` must call `RolloverScheduler.rearm()`** — an armed timer keeps its old fire date. A failed yearly log rotation (archive already exists) is warned about once and not retried; the log just keeps growing. One rollover: close the open session at the boundary → build an `ArchivedDay` → write it unless empty → rotate the log if the year changed → optionally reopen the same project at the boundary → `lastRollover = boundary`. An empty day writes nothing and still turns over. The plan's `RolloverEngine` was folded into `TimerEngine` because every step mutates state only the engine owns.
- `RolloverScheduler` decides *when*: a one-shot `Timer` for the next boundary (5s tolerance, weak target proxy, `.common`), re-armed after every run, plus `NSWorkspace.didWakeNotification` and `NSSystemClockDidChange` observers. Its notification tokens live in a small non-isolated box whose `deinit` removes them — a `@MainActor` class's `deinit` cannot touch non-`Sendable` stored values. Launch catch-up happens in `TimerEngine.init`, before anything is on screen; the scheduler only takes it from there.
- Archive rows are dated by the **tracking day**, `TrackingDay.dateString(for: TrackingDay.start(containing: lastRollover))`, so a manual reset files under the day it ended rather than the reset time. A second reset on the same day appends more rows for that date (and rewrites the markdown note); that is accepted, and belongs in the README.
- `ArchiveWriter` appends to `daily-summary.csv` / `sessions.csv` (header written only when the file is created) and overwrites `daily/YYYY-MM-DD.md`. Session timestamps are ISO-8601 with the local UTC offset via `ISO8601DateFormatter` pinned to `calendar.timeZone`. All escaping goes through `CSV.field` / `CSV.row` — which tests unicode **scalars**, because a CRLF is a single Swift `Character` and a grapheme-level search for `\n` walks past it.
- **`ArchiveLocation` is injected into `TimerEngine`** (`folder`/`fallbackFolder` closures, default `.standard` = the settings path or `~/Documents/Chronos`, falling back to `Application Support/Chronos/Archive`). Tests point both at a temp directory so they never touch `~/Documents` or the real app-support folder, and never trip the Documents TCC prompt.
- A failed archive write retries into the fallback folder and sets `TimerEngine.lastWarning`; the rollover always completes either way (the sessions are still in the JSONL log). Every swallowed persist error routes through `warn(_:)` (NSLog + `lastWarning`), and `MenuBarController` shows the warning as a disabled "⚠️ …" item with the full text as its tooltip plus a "Dismiss warning" item.
- An open session whose `start` is before `lastRollover` is closed at `lastRollover` on launch and filed on its own under the day it started (SPEC §6 "archive it to that day"); the catch-up loop only covers days from `lastRollover` onwards. In a log where another `open` follows it, `SessionLog` replay closes it first and the engine never sees it.
- `CGWindowListCreateImage` is obsoleted (macOS 15+); to screenshot the panel over the wallpaper, use ScreenCaptureKit with an `SCContentFilter` that excludes windows with `windowLayer >= 0`.
- **`TimerEngine.updateSettings { ... }` is the only way settings change**, and it stays the single writer of `state.json`. It returns the new `Settings` and deliberately does *not* touch the rollover schedule, because the engine does not own the scheduler: the settings window's rollover-time binding calls `AppDelegate`'s `onRolloverChanged`, which calls `RolloverScheduler.rearm()`. A no-op change writes nothing.
- **`SettingsWindowController`, `ReviewWindowController`, and `SessionEditorWindowController` are the three places in Chronos allowed to call `NSApp.activate(ignoringOtherApps:)`.** Everything else goes out of its way not to steal focus — the desktop panel never activates the app at all — but a window the user has just asked for has to come forward and take the keyboard, since Chronos is an `LSUIElement` agent and such a window would otherwise open behind whatever is frontmost and ignore every keystroke. All three are built once and reused (`isReleasedWhenClosed = false`), centred only on first open. Settings is `[.titled, .closable, .miniaturizable]` at 480x560 — the grouped `Form` scrolls, so the content is roughly 950pt tall inside it. Review is 560x720 in the panel's own Ink palette. The session editor is 520x420 in system appearance — it is a form of `DatePicker`s, and the project color dot is its only Chronos-palette touch — and owns a small `@Observable` `SessionEditorState` (just `projectFilter`) so a second "Edit today's sessions…" from another row re-filters the window that is already open instead of leaving it stuck on the old project.
- `SettingsView` uses `ForEach` inside a `Section`, **not a `List`**, for the project rows: a `List` nested in a grouped `Form` (itself a scroll view) collapses to an ambiguous height on macOS 14. Its `TextField`s need `.labelsHidden()` + `.multilineTextAlignment(.leading)`, or `Form` stacks its own "Name" label above each one and right-aligns the text.
- Project renames in Settings commit on Return or on losing focus, from a local `@State` draft — a per-keystroke binding fights the engine, which ignores a blank name.
- **A chosen archive folder is stored `~`-relative** (`abbreviatingWithTildeInPath`) when it is inside the home folder, and expanded again by `AppPaths.archiveDirectory(forSettingsPath:)`. A renamed home or a restored backup then still finds the archive; no absolute path is ever written to `state.json`.
- `LoginItem` wraps `SMAppService.mainApp`. **macOS, not `state.json`, is the truth about whether the app is registered** — the user can turn it off in System Settings without Chronos hearing. `settings.launchAtLogin` records intent, so `AppDelegate` calls `LoginItem.registerOnFirstLaunchIfWanted` only when the status is `.notRegistered`; a user who turned it off is left alone. `.requiresApproval` means registered-but-not-yet-allowed, and the settings window says "Approve in System Settings › General › Login Items". Failures show as an inline red caption, never an alert. Measured on this machine: a build run straight out of DerivedData reports `.notFound` (raw 3), not `.notRegistered`, so the first-launch registration is a no-op there — the intended `.notRegistered` path needs the app in `/Applications` (or anywhere LaunchServices knows about).
- `Exporter` reads the history off disk (`sessions.jsonl` plus every `sessions-YYYY.jsonl` beside it, deduped by session id), not from `TimerEngine.sessions`, which a yearly rotation has already trimmed. Rows are keyed by tracking day, so an export and `daily-summary.csv` agree; the `hours` column goes through the shared `TimeFormatting.decimalHours` that `ArchiveWriter` also uses.
- `ExportRange.thisWeek` / `.thisMonth` are anchored on the **tracking day** `now` falls in (so at 02:00 the export still covers yesterday's week) and use the calendar's own `firstWeekday`. `.custom` instead uses the plain calendar day of each picked date — a date picker hands back midnight, which is before an 04:00 rollover, and the user means the day they clicked.
- `CHRONOS_OPEN_SETTINGS=1` / `CHRONOS_OPEN_REVIEW=1` / `CHRONOS_OPEN_SESSIONS=1` in the environment make `AppDelegate` open that window at launch. Useful for screenshots: `CHRONOS_OPEN_REVIEW=1 Chronos.app/Contents/MacOS/Chronos` (`open` does not forward the variable).
- **The session editor is today-only** (sessions with `start >= lastRollover`) for three reasons stacked together, not one: a yearly rotation moves anything older out of the live `sessions.jsonl` into `sessions-YYYY.jsonl`; `SessionHistory`'s replay across those files is first-wins on session id rather than last-wins, so an `adjust` reaching a rotated file would be read in the wrong order; and the day it belongs to has already been written into the append-only archive CSVs, so correcting it would mean rewriting a filed day. Widening this later is a storage change (joint replay across files, plus re-archiving a day), not a UI change.
- **`TimerEngine.editSession`/`deleteSession` are append-first, exactly like `beginSession`**: the `adjust`/`delete` record is written to the log before `sessions[index]` is touched, and a failed append throws `.notRecorded` and leaves memory untouched — an edit the log never got is an edit that would vanish on relaunch anyway, so it is not applied in memory either. A no-op edit (nothing actually changed) appends nothing, like `updateSettings`.
- **`SessionEditing.instant(hour:minute:reference:dayStart:dayEnd:calendar:)`** exists because a `.hourAndMinute` `DatePicker` keeps the calendar day of whatever `Date` it was handed, which is wrong once the tracking day straddles midnight: for a session that started at 01:30 on an 04:00-rollover day, picking "23:00" means the previous evening, not 22 hours in the future. It builds the candidate on `reference`'s calendar day, then shifts it a day in whichever direction lands it inside `[dayStart, dayEnd)`; a time that fits nowhere in the window returns `nil` and the row leaves the draft alone. `SessionEditRow` calls it with `dayEnd = max(engine.nextRolloverBoundary, engine.clock.now().addingTimeInterval(1))`, not the boundary alone — an overdue rollover (the boundary has passed but `RolloverScheduler`'s timer hasn't fired yet) must not make "now" itself unpickable; the engine's own `endInFuture`/`notToday` checks still bound what Save actually accepts. On a spring-forward day, `Calendar.date(bySettingHour:minute:second:of:)` resolves a time inside the gap (02:30 on the 2026-03-08 change, say) to **03:00**, the first instant after it — not 03:30, which is what `Calendar.date(from:)` would give the same components.
- **`SessionEditRow` must not read `engine.now`** anywhere except the dedicated `RunningDurationLabel` subview — `engine.now` ticks once a second, and reading it from the row's own body would re-evaluate every `DatePicker` and the validation/overlap captions every second. Everything else that needs "now" (validation, the overlap caption, seeding "Stop at…") calls `engine.clock.now()` directly.
- `ChronosTests/TestSupport.swift`'s `at(year:month:day:hour:minute:)` is a free function, not an `XCTestCase` extension: a couple of test classes declare their own `at` against a different calendar, and a member on the shared superclass would make those (illegal) overrides instead of plain shadowing.
- **The bolt is one polygon, written down twice.** `BoltShape.points` (`Chronos/UI/BoltShape.swift`) and `boltPoints` in `Scripts/render-icons.swift` are the same six vertices in a unit box, y **down**; the SwiftUI shape maps them straight onto the rect, the script flips y for Core Graphics. `ChronosTests/BoltShapeTests.swift` pins the app-side list against a fixture copy, so a drift fails the tests. Changing the mark means changing all three together, then `swift Scripts/render-icons.swift` from the repo root and committing the regenerated PNGs.
- **`Scripts/render-icons.swift` owns every raster asset**: the ten `AppIcon.appiconset` PNGs (seven distinct pixel sizes — 16/32/64/128/256/512/1024 — filling ten slots) *and* that image set's `Contents.json`, the `MenuBarBoltIdle`/`MenuBarBoltRunning` template image sets, and `Assets/`. Hand-editing any of those files is wrong; edit the script. The icon is a macOS-style rounded square: 10% transparent margin, corner radius 22.4% of the body, Ink with a subtle vertical gradient to `#242832` at the top, bolt at 58% of the canvas.
- **The menu bar bolts are *template* images tinted by the button, not colored images.** `Contents.json` carries `"template-rendering-intent": "template"` for both, and `MenuBarController.refreshButton` sets `button.contentTintColor = Palette.scarlet.nsColor` while running and `nil` when idle. A colored (non-template) image would have to give up the vibrancy the menu bar applies. Do not set `isTemplate` in code — the catalog is the truth. Verify with `xcrun --sdk macosx assetutil --info .../Assets.car`.
- `ASSETCATALOG_COMPILER_APPICON_NAME` compiles the icon but does **not** write the plist key that points at it, so `project.yml`'s `info:` block sets `CFBundleIconName`/`CFBundleIconFile` explicitly. The `AppIcon.icns` that actool also emits only carries the 16/32/128/256 reps even in Release — that is expected; the full ten renditions live in `Assets.car`, which is what `CFBundleIconName` resolves against.
- The header bolt's start flicker is a `.phaseAnimator([1, 0.2, 1, 0.5, 1], trigger:)` driven by a counter that `.onChange(of: isRunning)` bumps — and never bumps under `accessibilityReduceMotion`, which parks the animator on the first (opaque) phase. First and last phases are both opaque so the bolt rests solid whichever phase the animator stops on. `HeaderView` takes `isRunning` as a parameter; `PanelView` passes `engine.openSession != nil`.
- `PanelController.inkTintAlpha` is **0.90**, measured, not guessed: rendering the panel over a bright and a saturated photographic wallpaper, 0.72 let the body drift 12/255 per channel between them (a visible color cast) with Muted text at 4.4:1, while 0.90 holds the drift to 4/255, Muted at 5.4:1 and Paper at 15:1, and still shows the desktop as a hint. Past ~0.94 the glass reads as flat paint.
- Screen capture may be unavailable to command-line tools on this machine: `CGGetActiveDisplayList` and `SCShareableContent.displays` both come back **empty** (window metadata and titles still list fine, and `CGPreflightScreenCaptureAccess()` returns true), so `screencapture` fails with "could not create image from rect" and the ScreenCaptureKit path from Phase 4 no longer works. To see the panel over a wallpaper, render it offscreen in a throwaway XCTest instead: an `NSImageView` with a wallpaper, an `NSVisualEffectView(.hudWindow)` in **`.withinWindow`** blending (which blurs the sibling behind it, standing in for `.behindWindow`'s compositor blur), the Ink tint, and an `NSHostingView(PanelView(...))` — then `cacheDisplay(in:to:)`. Note `xcodebuild` does not forward the shell environment to the test process, so such a scratch test has to hardcode its paths.
- **A test host cannot write into this repo.** `Data.write` from the XCTest process to a path on the external volume blocks forever inside `open()` (sampled: stuck in `__open`). Offscreen renders have to be written under `/private/tmp` and copied into `Assets/` from the shell afterwards. `Assets/screenshot-panel.png` (720x664, the panel at 2x over a generated dark gradient) was made that way with a throwaway `ScratchScreenshotTests`, deleted after; a custom `NSBitmapImageRep` at 2x pixel dimensions with `rep.size` left at the point size renders correctly through `cacheDisplay(in:to:)`, so 2x does not need a retina window.
- **`SessionHistory` is the one reader of the whole log set** (live `sessions.jsonl` plus every `sessions-YYYY.jsonl`, rotated years oldest first, deduped by id). `Exporter` and the review window both go through it, and `TimerEngine.sessionHistory` hands one out built on the engine's own log URL, so an injected temp log stays injected. Never read `engine.sessions` for anything older than today — a yearly rotation has already trimmed it.
- **`ReviewStats` is pure and `Calendar`-injected**, like `TrackingDay`: no clock, no disk, no `Calendar.current`. A session belongs to the day/week/month its **start** falls in and its time is clipped to that period's end (and to `now`), which is exactly the archive's rule, so the review and `daily-summary.csv` can never disagree. Week and month bounds are the calendar's own (its `firstWeekday` included) shifted from midnights to rollovers, so a period is always a whole number of tracking days; the previous week/month is found by stepping one second back from the current one's start, which is what makes a 28-day February work without arithmetic about it.
- `ReviewWindowController` is `[.titled, .closable, .miniaturizable]` at 560x720, plus `appearance = .darkAqua` and an Ink `backgroundColor` because it wears the panel's palette rather than the system's (see the three-activator gotcha above for why it, Settings, and the session editor call `NSApp.activate`).
- **The review snapshot is recomputed, never observed per second.** `ReviewScreen` owns `@State period` and `@State snapshot` and refreshes on `onAppear`, on `period`, on `engine.sessions` changing (start, stop, edit, delete), and from a 60s `Task` loop that dies with the window. Do **not** read `engine.now` in that body — it ticks once a second and the dashboard only shows whole minutes.
- Swift Charts is fine here (macOS 13+, part of the SDK, not a dependency). The daily chart plots `BarMark(x: .value(..., unit: .day))`, so it needs `.environment(\.calendar, snapshot.calendar)` and `.environment(\.timeZone, ...)` or it bins days in the machine's zone instead of the engine's — which is why `ReviewSnapshot` carries the calendar it was measured in. Bars are Muted except today's, which is Scarlet.
- The review bars use a fixed-width column (`ReviewView.barWidth`) with a proportional `Capsule`, deliberately **not** a `GeometryReader`: a reader in the middle of that stack fights the `ScrollView` for height. The averages table's three columns (`ReviewView.averageColumnWidth`, 88pt so "THIS MONTH" does not wrap) are fixed for the same reason, and its header row and value rows share those widths so the labels sit over their own numbers.
- **The review window has exactly one definition of "average": per *tracked* day.** Both the averages table and the daily chart's dashed rule divide by the tracking days that have **any** time on them, never by the days that have elapsed — `ReviewStats.trackedDayCount` for the table's three scopes, `ReviewStats.averageOnTrackedDays` for the chart. That is why the `Average on tracked days` insight line was dropped from `ReviewStats.insights`: the rule says it already, and the window should not state one number twice. Do not add a second average measured a different way without renaming both.
- **The all-time scope buckets sessions; it never walks the calendar.** `ReviewStats.allTimeRange` can be years wide, so `trackedDayCount` inserts `TrackingDay.start(containing:)` per session into a `Set<Date>` instead of stepping day by day — only a day carrying a session can be a tracked day, and a corrupt far-past timestamp therefore costs nothing. Two sessions on one tracking day must resolve to the identical instant for the set to dedupe them, which `testTwoSessionsOnOneDayAreOneTrackedDay` pins. `allTimeRange` also clamps its lower bound with `min(start, today)`: a future-dated session from a clock jump would otherwise build an inverted `Range`, and that traps.
- The averages table is deliberately **period-independent**, like the three headline tiles: its scopes are fixed at week/month/all-time, so `ReviewStats.averages(...)` takes no `ReviewPeriod` and the table does not move when the segmented control does.
- To eyeball a SwiftUI window without screen-recording access, render it offscreen instead of using `screencapture`: an `NSHostingView` in a plain `NSWindow`, `layoutSubtreeIfNeeded()`, spin `RunLoop.main` for a second, then `cacheDisplay(in:to:)` into a `bitmapImageRepForCachingDisplay`. Give it the full natural height (~1500pt) to see past the `Form`'s own scrolling.
